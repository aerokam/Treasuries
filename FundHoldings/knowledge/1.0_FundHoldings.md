## Purpose

A read-only table of Vanguard and F/m Treasury/TIPS fund holdings by CUSIP, enriched with ask/SA/SAO yield, term, and duration, plus fund-level weighted averages — so a fund's actual portfolio composition can be inspected security-by-security rather than trusting the fund's summary stats alone.

**Status:** this spec's File Layout, Enrichment Logic and Display sections describe the approved target design for the `FundHoldings/<TICKER>.csv` rename and the averaging-rule changes below. `updateAllHoldings.js`, `enrichHoldings.js` and `index.html` have not been changed to match yet — each section notes where it still describes the live code versus the target.

## Architecture — same shared R2 pipeline as every other app

FundHoldings follows the standard pattern: primary data lives in Cloudflare R2 ([S11](../../knowledge/DATA_DICTIONARY.md#s11)), populated by a scheduled Windows Task, and the browser reads only from R2 — no data is git-committed.

1. **Fetch** ([E7](../../knowledge/DATA_DICTIONARY.md#e7)/[E8](../../knowledge/DATA_DICTIONARY.md#e8)/[E9](../../knowledge/DATA_DICTIONARY.md#e9)/[E10](../../knowledge/DATA_DICTIONARY.md#e10)/[E11](../../knowledge/DATA_DICTIONARY.md#e11)/[E12](../../knowledge/DATA_DICTIONARY.md#e12)): `vanguard/updateVanguardHoldings.js`, `fminvest/updateFminvestHoldings.js`, `pimco/updateLtpzHoldings.js`, `schwab/updateSchpHoldings.js`, `bondbloxx/updateXhlfHoldings.js`, or `ishares/updateIcpiHoldings.js` writes `data/<TICKER>-Raw.csv` to a local scratch dir (gitignored). **Target** (not yet done): local only, not uploaded to R2 — only `enrichHoldings.js` reads it. **Live today:** writes `data/Holdings-<TICKER>.csv` and uploads it to R2 under `FundHoldings/` via `shared/upload.js`.
2. **Enrich**: `enrichHoldings.js` reads the raw CSV, cross-references R2 stores [S10](../../knowledge/DATA_DICTIONARY.md#s10) (TIPS: ask/SA/SAO yield) and [S7](../../knowledge/DATA_DICTIONARY.md#s7) (nominals: ask yield, coupon — filtered to non-TIPS rows of the combined `FidelityTreasuriesTips.csv` by the `Product` column) by CUSIP, computes `Term`/`Duration` via `shared/src/bond-math.js` (see Enrichment Logic below for the target averaging rules). **Target:** writes `data/<TICKER>.csv` locally in the layout below and uploads only this file to R2 — the pipeline's one upload. **Live today:** writes `data/Holdings-<TICKER>-Enriched.csv` and uploads it, in the old `CSV_HEADERS` shape (see Data Sources below).
3. **Display**: `index.html` fetches a holdings CSV (and, live today, `FundMeta.json`) directly from the public R2 URL, same as every other app's client-side fetch. **Target:** reads `<TICKER>.csv` alone — its metadata rows supersede `FundMeta.json` for this app once the switch is made; `FundMeta.json` itself is not deleted by this change, since nothing else is confirmed to depend on it.

**Automation**: `updateAllHoldings.js` runs steps 1–2 for every supported ticker (VBIL/VTIP/VTP via Vanguard, RBIL via fminvest, LTPZ via PIMCO, SCHP via Schwab, XHLF via BondBloxx, ICPI via iShares). Scheduled via Windows Task Scheduler (`FundHoldings`, daily 6:40am PT — registered in `scripts/setup-windows-tasks.ps1`), matching the cadence of the rest of the ingestion pipeline.

Adding a new fund: add its ticker to the `FUNDS` array in `index.html` and to the appropriate ticker list (`VANGUARD_TICKERS`/`FMINVEST_TICKERS`/`PIMCO_TICKERS`/`SCHWAB_TICKERS`/`BONDBLOXX_TICKERS`/`ISHARES_TICKERS`) in `updateAllHoldings.js`.

| Schwab Asset Management holdings export ([E10](../../knowledge/DATA_DICTIONARY.md#e10)) | `schwab/updateSchpHoldings.js` | SCHP | Requires Puppeteer (headless Chrome) — Schwab's site 403s plain HTTP requests (Akamai bot protection), confirmed by direct testing. | BondBloxx product-page holdings table ([E11](../../knowledge/DATA_DICTIONARY.md#e11)) | `bondbloxx/updateXhlfHoldings.js` | XHLF | No JSON/CSV API; the product page server-renders the full holdings table as static HTML, parsed directly (fund URL hardcoded per ticker). No Quantity/Coupon/Maturity Date columns — Coupon and Maturity Date are parsed from the `"US T BILL ZCP MM/DD/YY"` name suffix, same technique as fminvest's name-suffix parsing |
| BlackRock iShares ([E12](../../knowledge/DATA_DICTIONARY.md#e12)) | `ishares/updateIcpiHoldings.js` | ICPI | Plain CSV export, keyed by the fund's numeric `portfolioId` (hardcoded per ticker, no public ticker lookup); a preamble (fund name, as-of date) precedes the actual holdings table, so the header row is located by content rather than assumed at line 0. The source reports Duration/YTM/Real Duration/Real YTM columns, but these are discarded in favor of `enrichHoldings.js`'s computation so ICPI's figures stay comparable to every other fund's |

All six scrapers write the same `CSV_HEADERS` shape (`CUSIP, Holding Name, Ticker, Category, Quantity, Coupon, % of Fund, Market Value, Maturity Date, ISIN, SEDOL, As of`) to the raw file (unchanged by the rename below — only its name and R2 upload status change) and record fund metadata (`fundName`, provider id) to `FundMeta.json`, uploaded to R2 independently of the holdings file.

**MKTLIQ** (Vanguard) and **SSC GOVERNMENT MM GVMXX** (PIMCO and Schwab share the same State Street sweep vehicle), both cash-sweep vehicles, report a placeholder far-future maturity from their provider; `enrichHoldings.js` treats either as maturing tomorrow so `Term` reads as ~overnight rather than a meaningless multi-year figure.

<a id="file-layout"></a>
## File Layout — `FundHoldings/<TICKER>.csv` (target; not yet written by `enrichHoldings.js`)

Three parts in one file:

1. **Metadata** (row 1 a header, row 2 one data row), column-aligned to the table in part 2 below so the two rows share a visual grid: `Ticker` (CUSIP column), `Fund Name` (Holding Name column), `As of` (Maturity Date column), `Expense Ratio` (Coupon column, written as a percent, e.g. `0.06%`), a blank cell (% of Fund column), `Holdings` count (Market Value column), `30-Day SEC Yield` (Ask Yield column, written as a percent, e.g. `3.72%`). `Expense Ratio` and `30-Day SEC Yield` are each provider's own reported figure, the same two values `FundMeta.json`'s `expenseRatio`/`secYield` carry today, just percent-formatted here instead of percent-scale.
2. **Table** (row 3 a header, then one row per holding): `CUSIP, Holding Name, Maturity Date, Coupon, % of Fund, Market Value, Ask Yield, Term, Duration` — matching `index.html`'s `DISPLAY_COLS` exactly (see [Display](#display) below), `SA Yield`/`SAO Yield` inserted between `Ask Yield` and `Term` only for a fund with TIPS holdings. No column the app doesn't show: no `ISIN`, `SEDOL`, `Ticker`, `Category`, `Quantity`, or a per-row `As of` (all four of the first three and `As of` move to the metadata row instead; `ISIN`/`SEDOL`/`Category` are dropped entirely — the app's table never showed them). The `Term`/`Duration` headers carry their unit exactly as `index.html` already labels them (`Term (w)` or `Term (y)`; `Duration (y)`).
3. **Total row** (final row, no header): `Total / Wtg Avg` in the CUSIP column, blank Holding Name/Maturity Date; `% of Fund` and `Market Value` summed; `Coupon`, `Ask Yield`, `SA Yield`, `SAO Yield`, `Term`, `Duration` are Market Value-weighted averages (see Enrichment Logic below for which rows count toward each). Every numeric and percent value is written at full computed precision, not rounded for display — the file is a data export, not the rendered table.

<a id="enrichment-logic"></a>
## Enrichment Logic (`enrichHoldings.js`)

For each holding row, by CUSIP:
- **TIPS match** (found in [S10](../../knowledge/DATA_DICTIONARY.md#s10)): `Ask Yield`, `SA Yield`, `SAO Yield`, `Coupon` come from the S10 row.
- **Nominal match** (found in the non-TIPS rows of [S7](../../knowledge/DATA_DICTIONARY.md#s7)): `Ask Yield` = `Ask yield to maturity / 100`. No SA/SAO (nominals aren't seasonally adjusted).
- **No match** (cash/sweep lines, e.g. "US Dollar", MKTLIQ): `Ask Yield`/`Coupon` stay blank; excluded from weighted averages (see below).

In both match cases, the displayed `Coupon` always comes from the matched S10/S7 row (percent-scale, e.g. `6.75` for a 6.75% coupon — matching the convention every raw per-provider fetcher already writes), overwriting whatever the fund's raw export reported for that holding. This matters because a provider's export can round the coupon (e.g. BlackRock/ICPI reports `0.13` for the actual 0.125% coupon on the TIPS); S10/S7 are always full-precision.

CUSIP presence in the TIPS yield source (S10) is the source of truth for "is this a TIPS holding" — more reliable than the holding name text or a per-fund flag, and correctly handles a fund that mixes TIPS and nominal holdings (e.g., a fund holding both TIPS and short-term nominal bills).

`settle` is the run date (today, when `enrichHoldings.js` runs) — the same date [S7](../../knowledge/DATA_DICTIONARY.md#s7)'s Fidelity prices are quoted as of, and not necessarily the fund's `As of` date (the date the provider's holdings snapshot is as of, which can lag the run date by a day or more). `Term`/`Duration` are always measured from the run date for this reason.

`Term` = `termYears(settle, maturity)` (only if maturity is in the future). `Duration` = `calculateDuration(settle, maturity, coupon, askYield)` (only if term, coupon, and ask yield are all available) — **target** (not yet done): for a zero-coupon Treasury bill with a known maturity but no [S7](../../knowledge/DATA_DICTIONARY.md#s7) match (so no ask yield), `Duration` = `Term` instead of staying blank — exact for a zero-coupon instrument, whose Macaulay duration always equals its term. A holding that matured between the fund's `As of` date and the run date is left out of `Term`/`Duration` entirely, a known simplification.

<a id="display"></a>
## Display (`index.html`)

**Banner**: ticker, fund name, Expense Ratio, 30-Day SEC Yield, holdings count, and as-of date, in that order — any field missing is skipped rather than shown blank. **Live today:** Expense Ratio/SEC Yield come from `FundMeta.json` (percent-scale); holdings count is `rows.length` and as-of date is the first row's own `As of` column, both computed client-side from the enriched CSV. **Target:** all five come directly from `<TICKER>.csv`'s own metadata row ([File Layout](#file-layout) above) — `FundMeta.json` is no longer read by this app, though it is not deleted by this change. Either way, Expense Ratio and SEC Yield are each provider's own reported figure, not independently computed — unlike the holdings table's Ask/SA/SAO Yield and Duration, which are always `enrichHoldings.js`'s own cross-fund computation (see Enrichment Logic above).

**Columns** (display order): CUSIP, Holding Name, Maturity Date, Coupon, % of Fund, Market Value, Ask Yield, SA Yield, SAO Yield, Term, Duration. `SA Yield`/`SAO Yield` columns are omitted entirely for funds with no TIPS holdings (e.g., VBIL — all nominal Bills).

**Weighted averages** (footer row): `calcMktWtdAvg`, weighted by `Market Value`, over two different row populations:
- **Yield** (`Coupon`, `Ask Yield`, `SA Yield`, `SAO Yield`): rows with no [S10](../../knowledge/DATA_DICTIONARY.md#s10)/[S7](../../knowledge/DATA_DICTIONARY.md#s7) match (cash/sweep lines, and a bond with no Fidelity row) are excluded from the population entirely, not just zero-weighted — a cash line can carry a negative market value (e.g. "US Dollar") that would distort the weighted sum if merely down-weighted. No fallback to [FedInvest (E1)](../../knowledge/DATA_DICTIONARY.md#e1) for a bond [S7](../../knowledge/DATA_DICTIONARY.md#s7) doesn't carry — considered and rejected: added complexity, and a bill days from maturity has a yield dominated by price-rounding noise (roughly a 3.65 percentage-point yield swing per 0.001 of price on a one-day bill), undermining the fallback's own precision right where it would matter most.
- **Duration** (`Term`, `Duration`): every non-cash holding still outstanding at the run date counts, whether or not it has a yield match — **target**, not yet done; see Enrichment Logic above for the zero-coupon-bill imputation this relies on. Cash/sweep rows are excluded from this average too, the same as from Yield.

**Term unit**: displayed in weeks instead of years when every bond-row term is under one year (short-duration funds like VBIL read better as weeks-to-maturity).

**fminvest name cleanup**: fminvest-sourced `Holding Name` values embed the coupon/maturity suffix in the text itself (duplicating the Coupon/Maturity Date columns); this suffix is stripped for display only (a no-op for Vanguard-sourced names, which never carry it).

Tabs (one per ticker in `FUNDS`), column sort (click header, blanks always sort last, persists across tab switches so a sort like Maturity Date carries over when comparing funds), and drag-to-resize column widths (session-only, not persisted) — no server-side state.
