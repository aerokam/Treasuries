# 2.1 Export

**Importing** a holdings file or a DARA plan is specified at [4.2 Import holdings and DARA plan](./4.2_Import_Holdings_And_DARA_Plan.md), not here — this file covers export only: writing the app's own ladder back out as a file, for the next import cycle.

## CusipQty Export (Build / Rebalance)

The **CUSIP/Qty** option on the Export menu (`#export-menu-btn`, 6.0 §Import/Export Menus) produces a `cusip,qty,excess`-headered file from both Build and Rebalance output, directly re-importable on the next rebalancing cycle.

- **Build mode:** `qty` = `fundedYearQty`, `excess` = `excessQty` from the build details.
- **Rebalance mode:** `qty` = `fundedYearQtyAfter`, `excess` = `excessQtyAfter` from the rebalance details.
- Zero-quantity rows for PLI-zeroed years are included (as `qty=0,excess=0`) so the rebalance engine knows these rungs exist at zero cost.
- A `#fundedYear,dara` block (below) is appended from `summary.daraByYearResolved` so the re-import is an **exact, zero-trade round-trip**. This holds the durable per-year DARA intent — consistent with the per-year DARA shown in the Build and Rebalance UI — so the CSV and the UI carry the same information.

## `#fundedYear,dara` block (durable DARA intent — makes the round-trip exact)

Every export from our own app appends this block: a `#fundedYear,dara` marker line followed by one `year,amount` line for **every year in `[firstYear, lastYear]`**, including gap years (2037–2039) and future-30Y years (2057+) that have **no TIPS row**. The value is the resolved per-year DARA the build/rebalance actually used (`summary.daraByYearResolved`).

- **Why:** the held quantities alone do not pin the per-year DARA — build folds later-maturity interest, pre-ladder interest, cover excess, and 2052 AMD into each rung, and PLI-zeroed years show `0,0` which hides their DARA entirely. **Stating** the DARA removes all inference: a build → export → import → rebalance round-trip reproduces the ladder **exactly (zero trades)** for any shape — flat, user-edited per-year (variable), PLI, or future-30Y.
- **Coverage is NOT stored.** Only the per-year DARA (intent) is persisted, never "which TIPS cover which gap/future year." That attribution is recomputed by duration matching at rebalance time, since yields-at-the-time determine the actual trades.

## `#params` line (construction parameters DARA does not encode)

After the DARA block, our exports append a single `#params,key=value,...` line carrying the [Construction Parameters](../../knowledge/DATA_DICTIONARY.md#construction-parameters) DARA does not itself encode but that still change the target ladder:

- **`preLadderInterest`** (`true`/`false`) — when on, the pre-ladder coupon pool funds and **zeroes**
  the early rungs; with it off those same years hold real bonds. Two ladders with identical per-year
  DARA but different PLI are *different ladders*, so DARA alone cannot reproduce the target.
- **`maturityPref`** (`last`/`first`/`semiannual`/`all`) — which TIPS a funded year selects: latest-
  or earliest-maturing (one TIPS), Jan+Jul (semiannual, two TIPS out to ~10y), or one TIPS per
  distinct maturity month (`all`, quarterly ≤~2030, Jan/Jul ≤~2035, single Feb 2040+). See 2.0
  §Maturity Selection Within a Funded Year.
- **`couponPref`** (`higher`/`lower`) — for a maturity month with two TIPS issues (different
  coupons — Jan 2027/28/29, Apr 2028/29), which one the ladder buys. Only reachable via
  `maturityPref` values other than `last` (see 2.0 §Maturity Selection Within a Funded Year); the
  UI hides the control entirely for `last` since that policy can never land on a duplicate-issue
  month.
- **`availableCash`** (dollars, default `0`) — cash on hand the ladder is sized down against
  (2.0 §Available Cash). The superseded key `rmdCashOverride` is still **read** as an alias by
  import ([4.2.2](./4.2_Import_Holdings_And_DARA_Plan.md#parse-dara-plan-and-parameters)), so files
  written before the ladder-wide generalization keep working; it is never written.
- **`rmdCouponMode`** (`all`/`last`/`none`, default `all`) — the settlement year's
  remaining-coupon-counting choice (2.0 §Settlement-Year Coupon Treatment). Written by both this
  export and the standalone DARA-plan export (below), though the latter only emits the line when a
  value is non-default.
- **`refCpiDate`** (`YYYY-MM-DD`) — the Ref CPI date the file's DARA values are denominated at
  (3.0 §DARA Reference Date). Always written alongside a `#fundedYear,dara` block, since bare DARA
  numbers are meaningless without the basis they were stated in.

## Unified `Holdings` shape

Both CusipQty export and every import format produce or consume the same structure:

```js
[{ cusip: string, qty: number, excessQty?: number }, ...]
```

- `qty` — total holdings for this CUSIP (funded + excess).
- `excessQty` — excess quantity only (present from a CUSIP/Qty or tipsladder.com-format import; absent from a plain two-column or broker-format import).

When `excessQty` is present, the engine uses it to initialize that CUSIP's own funded/excess split
(`qty − excessQty` = its own funded quantity), rather than deriving it from DARA math. This preserves
the funded/excess split from the prior build across a rebalance cycle. The split is honored **per
CUSIP**, not per bracket year: a bracket year may hold a January and a July maturity at once (DD
§Bracket Year TIPS) — most commonly the Active Lower Bracket alongside an earlier-maturing Retained
Lower Bracket that happens to mature in the same calendar year (2.0 §Retained Bracket Excess) — and
each CUSIP's own stated `excessQty` is honored independently, never collapsed into a single
year-keyed figure.

## Standalone DARA-plan file (portable persistence, independent of holdings)

**Problem this solves:** the CusipQty export above only reproduces a DARA plan exactly when
re-importing *that same export* — but a real rebalancing cycle re-uploads a **fresh broker file**
(Vanguard/Fidelity/Schwab) each time, which never carries a `#fundedYear,dara` block (or any DARA
data at all) to overlay a plan onto. File load therefore always mirrors the fresh holdings with no
memory of a prior session's per-year shape (3.0 §Per-Year DARA from Portfolio). The standalone plan
file is the portable fix: it carries **only** the DARA intent, with **no CUSIP rows**, so it can be
exported once and re-applied on top of any subsequent fresh holdings upload, on any device.

**Structure:** the same `#fundedYear,dara` marker + `year,amount` lines used inside a CusipQty
export (above), but as the *entire* file:

```
#fundedYear,dara
2026,40000
2027,40000
...
2050,20000
```

**Export** (the **DARA Plan** option on the Export menu, `#export-menu-btn` — 6.0 §Row 1 / §Import/Export
Menus): writes the *current* `_daraByYearStore` (every year in the panel, sorted) to a downloadable
CSV. No CUSIP/qty data — this file says nothing about holdings, only about DARA intent. Also
appends a `#params,availableCash=...,rmdCouponMode=...` line (2.0 §Available Cash,
§Settlement-Year Coupon Treatment) when either is non-default — omitted entirely otherwise, so a
plan saved without touching either is a plain `#fundedYear,dara` file.

**Importing** this file — or a CusipQty export, for its DARA block and params — is [4.2.2 Parse DARA
plan and parameters](./4.2_Import_Holdings_And_DARA_Plan.md#parse-dara-plan-and-parameters).

**Not the same file as a CusipQty export.** A CusipQty export (`cusip,qty,excess` header) is a
*holdings* file that happens to carry the DARA block as metadata; a standalone plan file has no
header and no CUSIP rows at all — the two are detected differently (4.2.1: a CUSIP/Qty export keys
off the `cusip,qty,excess` header, which a standalone plan file never has) and serve different jobs
(reproduce a whole ladder vs. carry just the DARA intent across a fresh re-upload).

**No same-device cache.** An earlier localStorage "Save DARA Plan" cache offered to auto-apply a
remembered plan on every matching load; it surfaced its "saved plan found" prompt often enough to
be more annoying than useful and was removed. The standalone file above is the only persistence
mechanism now — used deliberately, not offered automatically.
