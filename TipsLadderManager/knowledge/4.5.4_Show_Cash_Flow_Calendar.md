## Cash Flow Calendar

A separate modal (`#cash-flow-overlay`/`#cash-flow-modal` in `index.html`), triggered by the **Cash
Flow** button in Row 2 (6.0 §Row 2). Answers a different question than the rest of the app: not "how
does this year's DARA get funded" but "when does my current portfolio actually pay me, and how much."
Independent of funded years, DARA, brackets, gaps, and Future 30Y covers — it is a fact about a
portfolio's actual held CUSIPs and quantities, not a ladder-construction result, so it is available as
soon as holdings are loaded, before Run (6.0 §Row 2). Draggable/resizable (6.0 §Modal Frame Standard)
— the calendar can run 30+ years deep, so resizing taller is expected to be common.

**Before/After toggle:** defaults to Before (`currentHoldingsArray` — what is actually held right
now, since that is what generates real cash flow today). In Rebalance mode, once a plan has been run
(`rebalanceRendered`), a second toggle button appears (`#cash-flow-toggle`, reusing the `.tab-btn`
pattern from the TipsRef Ref/Mkt toggle) letting the calendar preview After instead — the post-trade
target portfolio, built from the same per-CUSIP `qtyAfter` already shown in the rebalance table's Qty
After column (`rebalDetails[].qtyAfter`, summed by CUSIP; a CUSIP fully sold, `qtyAfter` 0, drops out).
The toggle is hidden in Build mode and before a plan has been run, since neither has an After state to
show. If the rebalance recommends no quantity change for a CUSIP, its contribution to Before and After
is identical (same real coupon/principal cash flow); the toggle previews the trade's actual effect on
future payments. This is a different question from the Amount popup's "Remaining later maturity interest"
([4.5.2 §Popup Routing](./4.5.2_Show_Drill_Popups.md#popup-routing), `amtBefore`/`amtAfter`): that figure is coupon income
feeding one year's DARA sizing, filtered to bonds maturing after the settlement year and (for the
settlement year) to not-yet-paid coupons only; the Cash Flow Calendar shows every held CUSIP's coupons
and principal with no such filtering. The two are not expected to reconcile to the same total.

**Amounts are penny-precise**, unlike every other dollar figure in this app (the main table's
`fmt: 'amt'`, and every other drill popup, round to the whole dollar). `_cfFm` (year/date rows) and
`fm2` (Level-3/4 drill popups, `src/drill.js`) both show two decimal places, and the CSV export
writes `amount.toFixed(2)` rather than a rounded integer. This calendar exists specifically to be
checked against a real brokerage statement, which posts to the cent — rounding would make an exact
comparison impossible.

**Scope:** actual held TIPS only — no synthetic TIPS for gap years or Future 30Y rungs, since those are
not real cash flows.

**Ref CPI: the Ref CPI of each payment date where published, and that of the settlement date otherwise.** The
Ref CPI series (`refCpiRows`) is published roughly 2 months ahead of the settlement date (3.0
§Ref CPI Date), so the first several payment dates in the calendar usually already have their
own published Ref CPI. Every payment date checks `lookupRefCpi(refCpiRows, thatDate)` first:
- **Published for that date (the common case for near-dated payments):** use it. This is the exception
  to how every other Amount figure in this app is priced, and is flagged as such in the drill-down
  (§Structure below) — `isActual: true`.
- **Not yet published (every other payment):** use the settlement date's value instead —
  `lookupRefCpi(refCpiRows, _defaultRefCpiDateStr)` — matching every other
  Amount figure in this app ([4.5.3 §Naming](./4.5.3_Show_Trade_Ticket.md#trade-ticket-naming)). That date (3.0 §Ref CPI Date) is never "today":
  popup copy must name the actual date in play rather than assume one.

**Cutoff: today, not the settlement/Ref CPI date — a payment is listed until its actual payment date
has arrived.** The rest of the app prices off the settlement date (`_defaultRefCpiDateStr`,
4.5.3 §Trade Ticket) because it is answering "what would a trade settle at." This calendar is answering
"has my portfolio paid me yet," so it walks from today (`_tradeDateStr`) instead. A payment is in the
account on its payment date, so a payment dated today is paid and is not listed. A coupon dated on a
weekend or bond holiday is actually paid on the next bond trading day (`actualPaymentDate`,
`shared/src/settlement.js`), so the event remains on the calendar, counted as unpaid, until that day,
even though its raw coupon date has already passed.

### Computation

```
today            = localDate(_tradeDateStr)                                  // start of the coupon walk — "has this been paid yet," not the trade-settlement date used elsewhere (4.5.3 §Trade Ticket)
walkFrom         = today − 10 days                                           // buffer so couponSchedule's forward walk doesn't miss a coupon delayed by a holiday weekend
dates            = couponSchedule(walkFrom, bond.maturity)                   // shared/src/bond-math.js — every coupon date from `walkFrom` through maturity inclusive
                     .filter(d => actualPaymentDate(d) > today)              // drop anything already paid: a payment dated today is paid today
// actualPaymentDate(d): d itself if d is a bond trading day, else nextBondTradingDay(d) — the weekend/holiday roll-forward
// per date d in dates:
actualRc         = lookupRefCpi(refCpiRows, isoDate(d))                      // that date's own published Ref CPI, or null
eventRc          = actualRc ?? lookupRefCpi(refCpiRows, _defaultRefCpiDateStr)
principalPerBond = bondCalcs(bond, eventRc).principalPerBond                 // TIPS Basics §Inflation-Adjusted Principal
couponPerBond    = principalPerBond × bond.coupon ÷ 2                        // one semiannual payment
```

For each held CUSIP, one coupon event is emitted per date in `dates` (amount = `couponPerBond × qty`),
each priced off that date's own `eventRc` — not one shared Ref CPI for the whole calendar. The final
date in `dates` always equals `bond.maturity`; that date additionally gets a principal event (amount =
`principalPerBond × qty`) — TIPS pay their last coupon and principal on the same day.
`couponSchedule` reuses the same coupon-date walk (`_nextCouponOnOrAfter` + semiannual stepping) that
`calculateDuration`/`yieldFromPrice`/`priceFromYield` already use, so the payment dates of a held TIPS here
always agree with its duration/yield calculations elsewhere in the app.

**Staleness:** Cash Flow's event list is computed once per open rather than live-bound, so
`_clearOutput()` closes the overlay and calls `hidePopup()` rather than leaving figures on screen
that no longer match what produced them.

### Structure: 4-level drill

Mirrors the funded-year group-header collapsible pattern ([4.5.1 §Funded Year Group Header Row](./4.5.1_Render_Ladder_Table.md#funded-year-group-header-row)) rather than
introducing a new interaction model:

1. **Year rows** — one collapsible row per calendar year present in the event list, showing that
   year's Coupon / Principal / Total. The current year is expanded by default; every other year starts
   collapsed. Clicking a year row toggles its date rows' `hidden` attribute (no popup).
2. **Date rows** (children of an expanded year) — one row per distinct payment date in that year,
   showing the date's Coupon / Principal / Total.
3. **Level-3 popup** (click a date cell) — `buildCashFlowDateDrill` (`drill.js`) — reuses `showPopup`
   (`popup.js`) directly with a plain row-descriptor array, the same mechanism as the Trade Ticket
   drill popups, not the colKey-routed `buildDrillHTML` used by the main table. Ref CPI is a single
   national series, not per-bond, so every event sharing a date shares the same `refCPI`/`isActual`
   (§Computation above) — shown **once**, at the top, rather than repeated per line:
   - **Label row** — `refCpiDateDisplay` as the value; label is `"Cpn Ref CPI date"` when `isActual`
     (that date's own date), or plain `"Ref CPI date"` otherwise (the settlement date) — the label
     itself flags the exception, no separate explanatory sentence.
   - **Ref CPI** — the numeric value used for every line below.
   - Then one line per CUSIP event (`<CUSIP> — Coupon` / `<CUSIP> — Principal`, its amount, rendered as
     a clickable `.cf-event-drill` span), followed by the date's total.
4. **Level-4 popup** (click a `.cf-event-drill` line) — `buildCashFlowEventDrill` (`drill.js`) shows
   how that one CUSIP's payment was calculated: Ref CPI → Dated Ref CPI → Index ratio → Inflation-Adjusted Principal per
   TIPS → (Coupon per period, for coupon events) → Coupon/Principal per TIPS → Quantity → Amount.
   Starts from the same Ref CPI value already shown at the top of Level-3 — nothing about which date
   it came from is repeated here. Routed via a `document`-level delegated click listener (matches the
   main table's `.drill-l3` nested-drill pattern, 4.5.2 §Nested (Level-3) drills) since the Level-3 popup
   is the body-level `#shared-popup` singleton, not a child of `#cash-flow-content`. Each event carries
   its own calc inputs (`qty`, `refCPI`, `baseCpi`, `indexRatio`, `principalPerBond`, `coupon`,
   `isActual`, `refCpiDateDisplay`) captured at `buildCashFlowData()` time, so this popup needs no
   re-lookup against `tipsMarketData` or `refCpiRows`.

### CSV Export

`#cash-flow-export` downloads the **full, flat, multi-year** event list regardless of which years are
expanded/collapsed in the modal — `Date,CUSIP,Type,Amount`, one row per coupon or principal event,
chronological. Same Blob/anchor-download pattern as Export CSV / Export CUSIP-Qty / DARA plan export.
